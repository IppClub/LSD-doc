# 技术与数据设计

状态：2026-10-03 设计与部分原型。现有路径相对 `Dora/LSD`；`Training/Recorder.lua` 和 `Training/Model.lua` 已有独立数据实现及原生建树验证，Arena 已实现真实 UnitAction 采集、独立战斗和固定站位试战；Level/Academy.Navigation 接入既有学院房间与统一 HUD。单学员模型持久化已接入；任务和完整存档系统尚未完成。

## 1. 实现策略

保留 Dora Platformer、Yue、Teal、TS/TSX、XML UI 和 Yarn 的现有组合。先核实编译及运行链路，再逐模块接业务，不为统一语言重写全部旧代码。`.yue/.tl/.ts/.tsx/.xml` 的生成 Lua 必须同步；当前多语言模块实际编译方式由运行基线任务记录。

现有 `Tutorial` 是动作与剧情教学基线，`Academy` 是基地导航基线。训练采集、模型、任务和存档独立于 UI 组件；UI 只显示状态并发出用户操作。

| 新增模块提案 | 职责 | 接入现有位置 |
| --- | --- | --- |
| `System/GameSession` | 新建、继续、阶段切换、退出与生命周期 | `Script/Start.yue` |
| `System/StoryProgress` | 剧情节点、选择、解锁、消息 | `UI/Story.yue`、`System/Command.yue`、Phone |
| `System/MissionService` | 任务前置、目标、结算幂等、奖励 | Academy、Formation、Settlement/MissionFail |
| `Training/Recorder` | 采样、合法动作标签、特征版本 | 实际 UnitAction 成功时点 |
| `Training/ModelService` | CSV 适配、异步建树、模型候选/采用/回滚 | Dora `ML.BuildDecisionTreeAsync` |
| `Training/Evaluator` | 固定种子试战、统计与可读反馈 | VRTraining 等可用场景 |
| `Battle/SquadController` | 导师/学员控制、指令、目标失效处理 | Platformer Decision 和 Actions |
| `Data/SaveRepository` | 版本化读写、备份、迁移、恢复 | 独立于显示配置；不直接覆盖现有 `lsd.db` |

模块名可在实现时调整，但职责和验收保持稳定。首次运行使用独立测试存档，保留用户现有 `/Users/Jin/Workspace/Dora/lsd.db`。

## 2. 状态与切换契约

主阶段：Title → NewGame/Continue → Opening/Tutorial → Academy → TrainingPrepare/Recording/Building/Evaluating/Review → Academy → Formation → Battle → Result → Academy；最终章节结果进入 Ending。

训练取消返回安全入口；建树回调带会话代次，退出或切场景后的旧回调不能采用模型。任务结果进入终态后禁止再次计算奖励。剧情、训练、任务三种状态分别持久化，不能共用单一“关卡编号”覆盖所有进度。

切换时统一解除事件、输入、计时器和协程，清理实体与不再引用的资源，再构建下一场景；不同任务不可复用残留 `Data.store` 状态。当前 entry/UI3D 的清理方式和数据库 attach/detach 生命周期要在基线中验证。

## 3. 数据对象

| 对象 | 建议最小字段 | 不变量 |
| --- | --- | --- |
| PlayerProfile | playerId、charId、displayName、createdAt | 新建时初始化；继续时不重写默认值 |
| StoryState | chapterId、completedNodes、answers、flags、readMessages | 节点和选项 ID 稳定；完成事件幂等 |
| MissionDefinition | missionId、prerequisites、sceneId、participants、objectives、failureRules、reward | 配置版本可追溯，胜负条件互斥 |
| MissionState | missionId、status、attemptId、claimedReward、resultSummary | 同一 attempt 只结算一次；奖励按设计一次性领取 |
| CharacterState | characterId、unlocks、growthFlags、skillLoadout、acceptedModelId | 模型采用与剧情成长分离 |
| TrainingSession | sessionId、characterId、enemyPresetId、skillIds、featureSchemaVersion、seed、samples、status | 未成功动作不产生动作标签；中止不改变已采用模型 |
| ModelRecord | modelId、version、characterId、featureSchemaVersion、actionSetVersion、tree、trainingSummary、evaluationSummary | 条件/动作白名单；保留上一采用版本 |
| Formation | formationId、memberIds、skillLoadouts、modelBindings | 不允许重复成员、未知技能和不兼容模型 |
| SaveEnvelope | schemaVersion、revision、profile、story、missions、characters、formations、modelRefs | 完整校验后替换；破损可退回备份 |

旧 `story.chnr.json` 的 Story/Conversation/Trigger/Progress 概念适合参考，不立即建 11 张同名表；Yarn 负责文案流，StoryState 负责事实。旧 `battle.chnr.json` 的 TrainData 和攻击属性可用于字段对照，首个切片先明确最小数据形状，避免同时引入完整仓库经济。

SQLite 与 JSON 的存储选择作为实现前技术验证项：既有 DB 可以复用事务，但需要迁移边界；JSON 便于小切片调试，但需原子写入和备份。默认提案优先在现有 SQLite 环境验证独立命名空间，未验证前不锁定格式。

## 4. 训练管线

1. Recorder 在动作被 UnitAction 接受时记录当前环境与动作 ID；连续移动/等待按重复状态去重并限制样本量；每次被接受的射击保留独立样本，避免丢失玩家示范频次。
2. 特征从真实可观测状态获得。首个实验候选为未朝向敌人、距离区间、敌方动作类别、攻击就绪和威胁窗口；CSV 列类型与标签格式按引擎当前接口及样例实测。
3. ModelService 把干净数据传给 `ML.BuildDecisionTreeAsync`，设置有限树深的候选值；具体深度通过验证集比较，不用接口 `maxDepth=0` 的无限制作为默认。
4. 将返回节点转换为声明式树结构；不把生成字符串直接当任意脚本执行。列名、操作符、标签和动作都限定为已知值。
5. 在 Unit Decision 适配层按条件选择合法动作；若预测动作不可用，执行显式 fallback 并计数。记录“模型决策”和“fallback 决策”，防止安全规则被统计成学会。
6. Evaluator 用独立种子和站位测试，保存对照数据；UI 显示候选，用户采用后更新 CharacterState，再保存。

模型要绑定角色/技能组/特征版本。更换武器或动作集合后，不能无提示复用旧树；提示复训或选择兼容版本。首版不依赖云端大模型或网络推理，当前 Codex 是开发工具，不能被混同为游戏 NPC 的学习机制。

## 5. 配置与内容校验

任务、角色、敌人和技能配置引用稳定 ID；启动开发校验应检查：ID 唯一、前置无环、引用存在、场景入口有效、胜负条件有定义、Yarn 节点存在、奖励可应用、Spine 资源及动作存在、音乐可加载。

给任务前置错误提供指向配置位置的诊断；开发快捷入口必须能创建满足前置的测试状态，并标识为开发测试，不成为普通玩家默认流程。

## 6. 存档与恢复

建议在任务开始前、采用模型后、任务结算/剧情节点结束后保存，保存成功才更新继续入口。失败回退到任务前安全点；中途退出训练丢弃未采用候选，除非后续显式增加训练草稿恢复。

维护上一有效版本，数据升级先备份再迁移；未知高版本不得静默覆盖。兼容旧 `Config` 时保留角色和开场偏好，不从旧 skipOP 自动推导“已完成教程/章节”。旧稿故事进度表不能直接作为已完成任务导入。

## 7. 性能与平台

先测一个训练场、一场任务和基地的加载时间、帧率及重复切换资源占用，再设预算。建树异步执行期间界面有状态与取消入口；运行中不得把全部样本同步打印到 HUD 导致卡顿。

原生 macOS 是第一个开发验证环境；Windows/Linux、Android/iOS 是发布范围的候选，需按实际包与设备逐个记录。Web 不作为当前原策划明确的首版平台依赖，可另列可选验证，不能借引擎 Web Runtime 的存在直接宣布游戏支持。

## 首切片的角色与动作映射（P04 核对稿）

以当前实际注册的 UnitAction ID 为执行依据，动画名称不等同于动作 ID。来源：`Tutorial/System.tl` 的角色动作集合、`Tutorial/Action.tsx` 的实现、`Tutorial/AI.yue` 的旧规则，以及 85 套 Spine 动画枚举。

| 角色资源 ID | 当前职责 | 可用于训练的动作 | 边界 |
| --- | --- | --- | --- |
| charM / charF | 玩家导师、当前教程控制对象 | kinetic、fmove、bmove、idle、turn | kinetic 损伤 HP；教学短按已分别取得男性和女性命中证据 |
| ninilite | 妮妮莉特，首切片学员 | laser、fmove、bmove、idle、turn | laser 损伤 AP；当前 AI:NPC/AI:NiniliteFight 是手写规则 |
| xiaotaotie | 教程敌人、训练与首任务敌人 | 教程沿用 blow 等动作；正式战斗支持 blow / swing / butt / roll / bomb 五种技能，详见下表 | 教程 HP/眩晕特殊规则不作为正式试战胜率评价；技能由公共 EnemyCombat 执行 |

第一轮训练选择直接接管学员 ninilite 做示范，停止该角色旧 AI 的决策后用同一合法动作集合采集与执行。这样模型标签仍是 laser，不把导师 kinetic 偷换为学员 laser；两者的伤害语义不同。该方案是接下来实现选择，尚未产生玩家示范学习的运行证据。

初版学习动作集合为 laser / fmove / bmove / idle。turn 作为可见且计数的执行前提处理，不能计入模型成功预测；fallOff、hit、dizzy、lose、cancel 归物理或战斗状态管理，不采作示范意图。显式等待必须通过真实可接受的 idle 动作记录。每个动作开始点采一条样本，按住移动不能每帧灌入重复样本。

攻击就绪特征必须来自训练执行器的真实冷却/可用状态；敌方 attack / recover / idle 必须由动作状态映射。未知动作需要明确归类和日志，不能将所有动画都猜成攻击。正式训练场还需替换教程特殊伤害规则，并保证采集时与试战时的特征计算一致。

## 训练场首次运行实现

`Training/Arena.lua` 默认测试可用 LoopTowerA；玩家训练采用已有 Scene.VRTraining / ninilite / xiaotaotie 和枪械资源，注册独立的 trainingLaser/Forward/Back/Wait 实体动作，训练标签保持 laser/fmove/bmove/idle。采样在 Unit.start 返回成功之后完成，但快照在提交之前获取，冷却拒绝不能变成样本。Record 接口与模型执行共享 snapshot/available/request，保证示范和试战状态语义一致。

正式训练原型以 HP 100、射击 20 伤害、0.8 秒冷却起步。敌人按五种技能循环执行自带前摇、事件攻击与恢复，其中甩尾挥击伤害 20；每场最多 35 秒。这些数值属于待调的原型参数。训练默认循环五种攻击（滚动本身带位移），首任务另开启待机追击；距离/技能选择与数值平衡仍需继续完善。

候选经三个固定站位 360/530/700 试战后才可采用；已有采用模型时在同样站位重跑原版本。modelActions / fallback / unavailable / turns / hits / damageTaken 分项计数；转向和拒绝不冒充学习成功。Progress/Store 在已挂载的游戏数据库内使用 Game0Training 独立表，将采用与上一模型同一事务保存。只有提交成功才更新界面成果；失败恢复原模型与候选。读取检查模型、特征、动作集合版本及合法角色/标签/规则；主记录无效可恢复有效备份，后续保存隔离损坏原文。未来版本记录保留且只读。该机制覆盖 JSON 记录损坏，尚不修复数据库文件损坏或跨版本迁移。

`Test/TrainingArena.lua` 用引擎脚本发出玩家动作请求，检查真实接受/拒绝、投射物命中、7 条示范建树及固定三场胜利，并验证采用后放弃新训练仍保留原版本。这不是原生手动输入验收，也不是所有示范都会胜利的保证。

训练示范覆盖起点：至少 6 条成功动作样本（连续移动/等待去重，成功射击逐次记录）、至少两种动作，不足时不产生候选并给出补练方向；不是机器学习收敛或泛化保证。场景 UI 显示动作分布和当前模型选择。现有缩放按钮禁止遗留的绝对 Scale 动画，以免点击后放大侵占相邻控件；学院入口依托原房门与传感器；训练室终端靠近后交互，训练菜单有完整触摸边界。

`Test/TrainingStore.lua` 覆盖重连、事务故障注入、备份恢复及未来版本保护；`Test/TrainingResume.lua` 在完整引擎退出重启后加载真实示范模型并实际试战。2026-10-03 revision=3 恢复采用/上一模型，hits=5、fallback=0。正式任务、多角色存档仍待实现。

## 攻击事件与动作恢复

训练与首任务共用 Arena：小饕餮直接完整播放素材 blow（自带前摇），不以固定秒数切断；素材 attack 事件只结算一次伤害，检查 310 距离内且目标位于攻击正面，AnimationEnd 后才切恢复阶段。3.4667 秒动画的命中事件约 1.684 秒，不将开始播放等同命中。

CombatAnimation 统一设置 playable.recovery=0.2，再播放新动作；人物素材有 prepare 则结束射击/停止移动回 prepare 循环，否则回 idle。怪物完整攻击后以同样恢复混合回素材已有的 prepare（无此动作则 idle），恢复阶段额外 1.1 秒是战斗冷却，不能截断动画。UnitAction.recovery 不等同 playable.recovery，前者不能替代姿态混合。死亡、清场和波次重置属于明确中断；普通松开移动不能截断正在射击的导师。

Mission.Service 将采用模型深拷贝为任务部署快照，Battle 用相同执行器驱动学员，导师独立真实移动/射击；两波和节点修复通过运行测试，尚未接正式任务 UI。

## 小饕餮技能恢复原策划

依据 `gamedoc/gameplay/game0/requirements/monster-spine-action.md` 小饕餮表，补齐五种技能，而非只复用教程 blow。实际 Spine 事件探测记录于 enemy-animation-catalog.txt：

| 策划技能 | 实际动画 | 动画时长/攻击点（秒） | 当前执行语义 |
| --- | --- | --- | --- |
| 甩尾挥击 | blow | 3.4667 / 1.700 | 正面单体伤害、横向击退 |
| 跳跃甩尾 | swing | 1.600 / 0.600 | 正面单体伤害，无击退 |
| 用角顶撞 | butt | 1.800 / 1.033 | 正面单体伤害、纵向击飞 |

| 滚动炸弹 | bomb | 2.2667 / 1.533 | 事件帧生成滚动投射物，碰撞触发范围伤害，无击退 |

roll 的策划名称在资源里拆为两个动画，没有独立 roll 循环。在图集中找到 taotiegungunjsonfuben/tucheng 球形素材（bounds 2,224,249,249），移动窗口复用它按位移速度旋转，接着完整播放 rollEnd；滚动停止边界读取当前Arena范围，城市坐标不会误触训练场350–1500范围；不伪造攻击事件或循环重播起势。炸弹没有独立图集贴图，使用 DrawNode 制作金属圆盘、亮芯和旋转效果，爆炸范围短暂显示后淡出。范围伤害按爆炸圆与实体矩形相交计算，避免以身体中心高度误排地面炸弹命中的对象。伤害、距离、速度和恢复冷却均为本轮实现参数，原策划只规定技能语义。

EnemyCombat 负责事件、滚动阶段和恢复，Arena 只保留统一 attack/recover/idle 特征供当前模型契约使用。普通动作不得改写正在攻击的动画；重置、死亡和清场可明确中断。横向/纵向击飞短暂禁止学员提交普通动作，避免下一帧移动立即抹去受击位移。首任务导师也是敌方技能可命中的实体，生命值进入任务报告。
